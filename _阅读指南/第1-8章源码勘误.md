| 原文判断 | 源码验证 | 说明 |
|---------|---------|------|
| UGUI 采用保留模式（Retained Mode） | ✅ 一致 | Dirty Flag 机制证实：属性变化时不立即重建，延迟到 CanvasUpdateRegistry 统一调度 |

## 第4章 UI 更新与重建系统

**无源码级错误，但有一处遗漏。**

| 原文判断 | 源码验证 | 说明 |
|---------|---------|------|
| Dirty Flag 延迟重建机制 | ✅ 一致 | SetVerticesDirty() 只打标记，不立即执行 |
| CanvasUpdateRegistry 是调度中心 | ✅ 一致 | 监听 Canvas.willRenderCanvases，在每帧渲染前执行 PerformUpdate() |
| Layout Rebuild 和 Graphic Rebuild 是两阶段 | ✅ 一致 | Layout(0-2) → ClipperRegistry.Cull → Graphic(3-4) |

## 第5章 Graphic 系统

**无源码级错误。**

| 原文判断 | 源码验证 | 说明 |
|---------|---------|------|
| Graphic 继承 UIBehaviour，实现 ICanvasElement | ✅ 一致 | `Graphic : UIBehaviour, ICanvasElement` |

| SetVerticesDirty → 注册到 CanvasUpdateRegistry | ✅ 一致 | `CanvasUpdateRegistry.RegisterCanvasElementForGraphicRebuild(this)` |
| Rebuild → UpdateGeometry → OnPopulateMesh → CanvasRenderer.SetMesh | ✅ 一致 | 完整链路与源码一致 |
| Image/Text 通过重写 OnPopulateMesh 生成不同网格 | ✅ 一致 | Image.cs 和 Text.cs 各自实现 |

### 补充细节（不构成错误，但可更精确）

SetVerticesDirty 内部做了两件事：

```csharp
public virtual void SetVerticesDirty() {
    if (!IsActive()) return;
    m_VertsDirty = true;
    CanvasUpdateRegistry.RegisterCanvasElementForGraphicRebuild(this);
    m_OnDirtyVertsCallback?.Invoke();
}
```

SetMaterialDirty 同理，但设置的是 `m_MaterialDirty`。两者都加入同一个 `m_GraphicRebuildQueue`，在下一帧 PreRender 阶段由 Rebuild() 根据具体脏标记分别处理。

## 第6章 Canvas 系统

**无源码级错误。**

| 原文判断 | 源码验证 | 说明 |
|---------|---------|------|
| Canvas 有三种渲染模式 | ✅ 一致 | `Canvas.renderMode`: ScreenSpaceOverlay / ScreenSpaceCamera / WorldSpace |
| Overlay 模式不依赖 Camera | ✅ 一致 | overlay 模式下 worldCamera 为 null |
| Canvas 执行批处理（BuildBatch） | ✅ 一致 | 但 BuildBatch 是 native 方法，C# 侧不可见 |
| Canvas 是 Batch 的边界 | ✅ 一致 | 不同 Canvas 的 UI 不会合并 Batch |

### 补充：排序规则

原文提到了 Sorting Order 是排序因素之一。更精确的排序优先级：

**Overlay 模式**：`sortingOrder`（升序）→ Hierarchy 顺序
**Camera/WorldSpace 模式**：Camera Depth（升序）→ Sorting Layer（升序）→ `sortingOrder`（升序）→ `planeDistance`（降序）

## 第8章 UI 批处理与 DrawCall

**无源码级错误。**

BuildBatch 是 native 方法（C# 侧不可见），所以本章内容无法通过源码逐行验证。但通过 Frame Debugger 的实际观察和 Unity 官方文档的描述，本章的以下判断与引擎实际行为一致：

| 原文判断 | 验证方式 | 说明 |
|---------|---------|------|
| 批处理将多个 UI 合并为同一次 DrawCall | Frame Debugger 观察 | 同材质+同纹理+同渲染状态的 UI 出现在同一个 DrawCall 中 |
| 材质变化打断 Batch | Frame Debugger → Different Material | 验证通过 |
| 纹理变化打断 Batch | Frame Debugger → Different Texture | 验证通过 |
| Mask 打断 Batch | Frame Debugger → Different Stencil | 验证通过 |
| DrawCall 的本质是 GPU 状态切换 | GPU 渲染原理 | 通用知识 |
