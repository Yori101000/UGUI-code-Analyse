# 第16章 文本渲染系统

> 本文是对原文的结构化重写。原文 15.1、15.2、15.3 中"动态图集→textureRebuilt→SetAllDirty→Canvas 级联刷新"同一链路重复了三次以上，15.5 排版系统 18 个小节深入字体排印通识但与 UGUI 机制关联较弱。现合并为 6 节，按初学者路径自底向上：字符→图集→动态更新→Text 渲染流程→TMP→优化。对照 UGUI 源码修正了 5 处错误/不准确表述。

---

## 概述

文本渲染和 Image 渲染本质上的不同：

```
Image 渲染：固定 Sprite → 固定 UV → 一个 Quad（4 顶点）→ GPU
Text 渲染：字符串 → 逐个字符查字体 → 动态生成 Quad 网格 → GPU
```

Image 固定 4 个顶点，Text 每多一个字符就多 4 个顶点。100 个字的文本 = 400+ 顶点，这就是为什么大量文本比大量 Image 更消耗 CPU。

---

## 16.1 从字符到像素：文本渲染的完整链路

### 16.1.1 两个基础概念

**字符（Character）≠ 字形（Glyph）**

- **字符**是逻辑层面——Unicode 编码，如 `U+0041` 代表字母 "A"。它只告诉你"这是什么符号"，不包含图形信息。
- **字形（Glyph）**是视觉层面——"这个字符在当前字体下长什么样"。同一个字符 "A" 在宋体、黑体、Arial 里看起来都不一样。

文本渲染系统操作的是 Glyph，不是 Character。它的工作：拿到字符串 → 逐字符查对应 Glyph → 找到该 Glyph 在图集中的 UV → 生成 Quad。

**字体文件（.ttf/.otf）≠ 字形图集（Font Atlas）**

- **字体文件**保存的是矢量曲线（贝塞尔曲线），描述每个字符的轮廓。分辨率无关，放大不会模糊。
- **字形图集**是 GPU 真正使用的纹理。GPU 不能渲染贝塞尔曲线，需要先把矢量轮廓转成像素——这个过程叫**栅格化（Rasterization）**，由操作系统底层的 FreeType 库完成，不是 Unity C# 代码直接做的。

类比：字体文件是"建筑图纸"（矢量，可任意缩放），字形图集是"拍好的照片"（像素，固定分辨率）。渲染时 GPU 用的是照片。

### 16.1.2 字形图集：一张纹理放所有字符

GPU 不希望每渲染一个字符就切换一次纹理（会打断 Batch）。系统把多个字符的栅格化结果打包到同一张纹理——**字形图集（Glyph Atlas）**：

```
┌──────────────────────────┐
│  [A]  [B]  [C]  [D]     │
│  [E]  [F]  [中] [文]    │
│  [你] [好]              │
└──────────────────────────┘
```

每个字符在图集中占据一块矩形区域。渲染 "A" 时，系统用 UV 坐标告诉 GPU："去图集左上角采样那块"。一块图集纹理 = 所有字符共享 = 可以合批。

**Advance（前进距离）**：渲染完一个字符后，光标往右移动多少像素才画下一个字符。比如 "A" 的 Advance=20，"B" 的 Advance=18。文本排版本质上就是不断累加 Advance：`cursorX += glyph.advance`。

### 16.1.3 静态 vs 动态字体图集

| | 静态图集 | 动态图集 |
|------|------|------|
| 何时生成 | 编辑阶段一次性烘焙 | 运行时按需生成 |
| 字符范围 | 预先指定（如 ASCII 全集） | 用到什么生成什么 |
| 运行时性能 | 稳定，无额外开销 | 首次遇到新字符时卡顿 |
| 内存 | 固定、可预估 | 随使用增长 |
| 适合场景 | 英文项目、字符集固定 | 中文项目、聊天系统 |

**中文字符数以万计**——GB2312 6000+ 字，CJK 全集数万字。全部预烘焙到一张图集会超过硬件纹理尺寸限制，所以中文项目必然用动态图集。

**动态图集的致命问题：纹理空间是有限的。** 图集满了（如 1024² 纹理装不下更多字），系统面临选择：**扩容**（512→1024→2048，显存增加）或**重建**（重新排列字符位置 → 所有旧 UV 失效）。无论哪种，纹理内容变了，就会触发级联反应。

## 16.2 Font.textureRebuilt：文本系统最关键的性能链路

一次图集更新，影响所有使用该字体的 Text 组件：

```
字体图集纹理发生变化
  ↓
Font.textureRebuilt 事件触发
  ↓
FontUpdateTracker 找到所有引用该字体的 Text
  ↓
每个 Text.FontTextureChanged()
  ↓
SetAllDirty() → Layout Dirty + Vertex Dirty + Material Dirty
  ↓
下一帧 CanvasUpdateRegistry 统一执行 Rebuild
  ↓
所有 Text 重新排版 → 重新生成 Mesh → Canvas 重新 Batch
```

**关键**：不是"变了一个 Text"。界面有 50 个 Text 用同一动态字体 → 图集一次更新 → 50 个 Text 全部重建 → Canvas 整批刷新。

这就是聊天界面首次打开卡顿的原因：动态图集首次遇到几十上百个新汉字 → 密集栅格化 + 图集写入 → 可能触发多次 textureRebuilt → 所有 Text 反复重建。

**Font.RequestCharactersInTexture()** 是 Unity C# 层主动请求字符生成的 API：

```csharp
font.RequestCharactersInTexture("你好世界");
```

调用后 native 层（FreeType）执行栅格化，结果写入字体图集。`Font.GetCharacterInfo()` 获取单个字符的 UV、Advance 等信息——Text 组件最终基于这些数据生成 Mesh。

## 16.3 UGUI Text 的渲染流程

### 16.3.1 Text 在 Graphic 体系中的位置

```
Graphic
  └── MaskableGraphic
       └── Text
```

Text 和 Image 是兄弟——都继承 MaskableGraphic，都走 `Graphic.OnPopulateMesh() → CanvasRenderer.SetMesh() → Canvas.BuildBatch() → GPU`。区别在 **OnPopulateMesh 里做了什么**：Image 拿 Sprite 的 UV 拼一个 Quad，Text 走一整条"字符串→排版→顶点"链路。

### 16.3.2 修改 text 后：延迟刷新

```csharp
text.text = "Hello";
```

不是立刻渲染——UGUI 使用延迟刷新：

```
text.text = "Hello"
  → SetVerticesDirty()    // 标记顶点需要重新生成
  → SetLayoutDirty()      // 标记布局尺寸可能变化
    → CanvasUpdateRegistry.RegisterCanvasElementForGraphicRebuild(this)
      → 等下一帧 Canvas 统一调用 Rebuild()
```

一帧内改三次 text，只执行一次重建。

### 16.3.3 TextGenerator.PopulateWithErrors()：整个链路的核心

Canvas 下一帧 Rebuild 时，`Graphic.Rebuild() → UpdateGeometry() → OnPopulateMesh()` 内部调用 `cachedTextGenerator.PopulateWithErrors()`：

```
cachedTextGenerator.PopulateWithErrors(字符串, settings, gameObject)
  ├── ① 逐字符遍历
  │     检查每个字符是否在字体图集中
  │     不在 → 请求动态字体生成（栅格化 + 写入图集）
  │
  ├── ② 排版计算
  │     累加 Advance 确定每个字符的 X 位置
  │     判断是否超出宽度 → 决定换行
  │     根据对齐方式调整整行偏移
  │
  └── ③ 生成顶点（每个字符一个 Quad）
        4 顶点 + 2 三角形 + UV（从图集取字符区域）
        + Vertex Color（text.color）
          → 写入 VertexHelper → 生成 Mesh → CanvasRenderer.SetMesh()
```

每个字符 = 1 个 Quad = 4 顶点 + 2 三角形。100 字 = 400 顶点——比 Image 的 4 顶点大了 100 倍。**这是文本 CPU 开销的根源。**

### 16.3.4 文本合批

Text 合批和 Image 规则相同——同一个 Material 实例 + 同一张 Texture：

```
Text A → Arial 图集 → 材质 M
Text B → Arial 图集 → 材质 M
→ 同一材质 + 同一纹理 → 可以合批 ✅

Text A → Arial 图集
Text B → 宋体图集
→ 不同纹理 → 无法合批 ❌
```

动态图集更新后 → 图集纹理变了 → 材质引用可能变 → Batch 被打断。这就是文本系统是 DrawCall 高频来源的原因。

### 16.3.5 Best Fit 和 Rich Text 的代价

- **Best Fit**（自动缩放）：当文本内容超出固定区域时，自动缩小字号使其刚好适合。它的实现方式是**逐个字号暴力尝试**——从最大字号开始，每次减 1，每试一次都完整执行一次 Populate()（字符解析 + 排版 + 顶点生成），直到测量宽度能放进 RectTransform。例如字号范围 20~40，"Hello World" 在 40 号字时宽度 300 像素超出 200 像素的固定区域：试 40→39→38→…→23，共 18 次 Populate()。正常 1 个 Text 只调 1 次 Populate()，Best Fit 让 1 个 Text 调了几十次，全部在同一帧完成。大型项目几乎都禁用。
- **Rich Text —— 不仅是解析成本，还涉及顶点和 DrawCall**：
  
  **传统 Text：**
  
  | 标签 | 对顶点的影响 | 对 Batch 的影响 |
  |------|:---:|:---:|
  | `<b>` | ❌ **翻倍**（同一个字符渲染两次，第 2 次偏移 1~2px） | 无 |
  | `<i>` | ✅ 无（只做剪切变换） | 无 |
  | `<size>` / `<color>` | ✅ 无 | 无 |
  | `<material>` | ✅ 无 | ❌ **打断**（材质引用不同） |
  | `<quad>` | +4 顶点/个 | 无 |
  
  `<b>` 是最容易被低估的——"Hello" 5 个字正常 20 顶点，加粗后变 40 顶点，翻了一倍。因为传统 Text 的粗体不是换字体，是**重复渲染 + 偏移**。
  
  **TextMeshPro：**
  
  | 标签 | 对顶点的影响 | 对 Batch 的影响 |
  |------|:---:|:---:|
  | `<b>` | ✅ **无**（SDF 参数模拟，不额外生成几何） | 无 |
  | `<u>` / `<s>` / `<mark>` | +4 顶点/段（下划线/删除线/高亮是额外几何） | 无 |
  | `<sprite>` | +4 顶点/个 | ❌ **可能**（不同材质 → TMP_SubMeshUI → +1 DrawCall） |
  | `<font>` | ✅ 无 | ❌ **可能**（不同图集 → TMP_SubMeshUI → +1 DrawCall） |
  | `<gradient>` | ✅ 无 | ❌ **可能**（不同材质 → TMP_SubMeshUI → +1 DrawCall） |
  | `<voffset>` / `<sup>` / `<sub>` | ✅ 无 | 无 |
  | `<link>` | ✅ 无 | 无 |
  
  TMP 加粗不减顶点（比传统 Text 好），但 `<u>`/`<s>`/`<mark>` 是额外生成的几何图形，不是字符的一部分。而 `<sprite>` / `<font>` / `<gradient>` 如果使用不同材质，会触发 `TMP_SubMeshUI` 创建——**每个 SubMesh 产生一个独立 DrawCall**，这才是 TMP Rich Text 最需要注意的性能点。

## 16.4 TextMeshPro：SDF 字体 + 独立文本引擎

### 16.4.1 SDF 渲染原理

传统 UGUI Text 字体图集存**像素颜色**——字符被栅格化成固定分辨率的位图。放大 3 倍 → 像素拉伸 → 模糊。

TMP 字体图集存 **Signed Distance Field（SDF，有符号距离场）**，每个像素存的是**到字符边缘的距离**，不是颜色：

```
传统位图纹理：
  [黑][黑][黑][灰][白][白]  ← 存颜色
  放大后：块状锯齿

SDF 纹理：
  [-3][-2][-1][0][+1][+2][+3]  ← 存距离
  Shader 实时算："距离 > 0.5 → 在字符外 → 透明"
  放大后：边缘平滑（距离场可平滑插值）
```

边缘信息是 Shader 从距离场实时计算的，不固化在纹理里，放多大都不锯齿。这就是 TMP 文本质量远超传统 Text 的根本原因。

以 8-bit SDF 纹理为例，像素值含义：

```
  -127  -64   0   +64  +127
  外部  外部  边界  内部  内部
```

正值表示像素在字形内部，负值在外部，0 恰好落在轮廓边界上。Shader 通过插值距离值，在任意缩放下恢复清晰轮廓。SDF 纹理在**导入字体资产时**生成，不在运行时执行：

```
TTF/OTF 字体文件
  → 提取 glyph 轮廓曲线（矢量路径）
  → 对每个像素计算到最近轮廓的距离
  → 写入 SDF 纹理（通常是 8-bit 或 16-bit）
```

SDF 参数通过 `UIVertex.uv2` 传递给 Shader，因此使用 TMP 时需要开启 Canvas 的 TexCoord2 通道（AdditionalShaderChannels）。

### 16.4.2 SDF 的附加福利

描边、阴影、发光、柔化全部在同一个 SDF Shader 内完成，不需要额外 DrawCall。传统 Text 做描边要渲染多层文本叠加。

### 16.4.3 TMP 的源码结构与继承

TMP 是独立包 **`com.unity.textmeshpro`**（源码仓库：Unity-Technologies/TextMeshPro），**不在 uGUI 仓库中**。其源码结构如下：

```
com.unity.textmeshpro/Scripts/Runtime/
├── TMP_Text.cs                  ← 抽象基类，类似 Graphic 的地位
├── TextMeshProUGUI.cs           ← UGUI 组件（挂载在 GameObject 上）
├── TMP_FontAsset.cs             ← 字体资产
├── TMP_SpriteAsset.cs           ← Sprite 图集（Emoji 支持）
├── TMP_TextInfo.cs              ← 文本布局信息
├── TMP_MeshInfo.cs              ← Mesh 数据结构
├── TMP_CharacterInfo.cs         ← 字符信息
├── TMP_LineInfo.cs              ← 行信息
├── MaterialManager.cs           ← 材质管理
├── ShaderUtilities.cs           ← Shader 工具
└── TMP_Settings.cs              ← 全局设置
```

继承关系：

```
MonoBehaviour
  └── TMP_Text（实现 ICanvasElement、IMaterialModifier 等）
       ├── TextMeshProUGUI（UGUI 集成，挂在 GameObject 上）
       └── TextMeshPro（World Space 3D 文本）
```

TMP **不继承 Graphic**，是一个独立文本系统，但实现了 `ICanvasElement`，同样走 `CanvasUpdateRegistry` 的调度流程。它也不用 Unity 的 Font 对象，而是用预构建 SDF 图集的 `TMP_FontAsset`，运行时不需要逐字符动态栅格化（除非遇到不在图集中的字符）。

### 16.4.4 字符缓存系统

TMP 的核心性能优化是字符缓存。`TMP_TextInfo` 缓存三类数据：

```
TMP_TextInfo
├── characterInfo[]      ← 每个字符的排版信息（索引、位置、尺寸、UV）
├── meshInfo[]           ← Mesh 数据（顶点、UV、三角形）
└── lineInfo[]           ← 行信息（行高、基线偏移等）
```

文本变化时不是全量重建，而是复用已有缓存，只重新排布变化部分：

```csharp
// TMP_Text.cs（简化）
public void SetText(string text)
{
    // 1. 解析富文本标签
    // 2. 复用现有字符缓存，只重新排布变化的部分
    // 3. 更新 TMP_TextInfo
    // 4. 标记顶点 dirty，触发 Mesh 重建
}
```

这与传统 Text 每帧 `cachedTextGenerator.PopulateWithErrors()` 形成对比：TMP 的排版缓存避免了重复的字体加载和字形定位，字符数不变时不触发全量排版。

### 16.4.5 多 Atlas 纹理与动态图集稳定性

传统 Text 只有一张图集纹理，满了之后只能扩容或踢旧字符。扩容会让所有旧字符的 UV 位置全变，触发 `textureRebuilt` 级联重建；达到硬件上限后只能踢字符，新字符和常用字符交替出现时图集反复横跳，可能每帧触发重建，最终表现为缺字 □。

**TMP 的 Multi Atlas：** 第一张图集满了就新建第二张，旧图集上的字符 UV 全部保持不变，使用旧字符的 Text 不需要重建，只有用到新字符的 Text 更新 UV：

```
新字符写入流程
  → Atlas 0 有空位吗？
    → 有 → 写入 Atlas 0
    → 没有 → Atlas 1 有空位吗？
      → 有 → 写入 Atlas 1
      → 没有 → 新建 Atlas 2 → 写入 Atlas 2
```

一张 1024² 的 SDF 图集可容纳成百上千字符，多数时候新字符直接写入当前 Atlas 空闲区域。Multi Atlas 真正的价值是**当真的满时，旧图集不受影响**，避免了"一个生僻字导致所有 Text 全部重建"的级联灾难。TMP 通常限制最大 Atlas 数量（4~8 张），达到上限且没有空位时才会做强制清理。

代价是跨 Atlas 的字符无法合批，同一段文字中 ASCII 字符和 Emoji 各产生一个 DrawCall。

### 16.4.6 材质系统

TMP 使用多种预设材质：

| 材质类型 | 效果 | 顶点倍数 |
|---------|------|---------|
| `TMP_SDF-Mobile` | 基础 SDF | 1× |
| `TMP_SDF-Mobile Overlay` | 叠加 SDF | 1× |
| `TMP_SDF-Mobile Masking` | 带 Mask 支持 | 1× |
| `TMP_Bitmap-Mobile` | 回退到位图 | 1× |
| 自定义 Outline | SDF + 描边 | ~2× |
| 自定义 Glow | SDF + 发光 | ~2× |

TMP 支持 5 层材质（Face、Outline、Underlay、Overlay、Glow），启用越多层，每字符生成顶点数越多。文本内混用不同材质时自动生成 `TMP_SubMeshUI` 子对象，每个 SubMesh 产生一个独立 DrawCall。

### 16.4.7 TMP 的代价

- **顶点数据更多**：每个字符需额外存 Normal、Tangent 等信息供 SDF Shader 使用
- **SDF Shader 更重**：传统 UI Shader 几乎不算，SDF Shader 要读距离场、算边缘、做描边和发光
- **SubMesh 增加 DrawCall**：文本中混入 Sprite、字体切换、渐变等不同材质内容时，每个 `TMP_SubMeshUI` 产生一个独立 DrawCall，大量使用 Sprite/Emoji 的文本 Batch 数会明显偏高
- **RichText 解析开销**：TMP 支持更丰富的标签（`<link>`、`<sprite>`、`<gradient>`），解析成本更高

## 16.5 TMP vs 传统 Text 对比

| 维度 | 传统 UGUI Text | TextMeshPro |
|------|---------------|-------------|
| 字体纹理 | 位图（像素颜色） | SDF（距离场） |
| 缩放质量 | 放大模糊、锯齿 | 锐利（边缘实时计算） |
| 动态图集 | 单张，扩容/重建影响所有 Text | Multi Atlas，新建不影响旧图集 |
| 文本特效 | 需额外 DrawCall 或组件 | Shader 内完成（Outline/Glow/Shadow） |
| 排版能力 | 基础换行 + 对齐 | Unicode Line Breaking、Kerning、多语言 |
| 富文本 | 有限支持 | 完整支持（link/sprite/gradient 等） |
| 字体资产 | Font（运行时栅格化） | TMP_FontAsset（导入时预构建 SDF） |
| 批处理条件 | 同材质同纹理 | 同 Atlas 纹理（跨 Atlas 断批） |
| UV 通道 | uv0 | uv0 + uv2（SDF 参数） |
| 源码位置 | `UI/Core/Text.cs`（uGUI 仓库） | `Scripts/Runtime/TMP_Text.cs`（com.unity.textmeshpro 包） |
| 基类 | MaskableGraphic | TMP_Text（独立体系，实现 ICanvasElement） |
| CPU（单次更新） | 较低 | 较高（顶点更多、RichText 解析更重） |
| GPU | 较低（简单 Shader） | 较高（SDF Shader） |
| 动态图集稳定性 | 差（textureRebuilt 级联刷新） | 好（Multi Atlas 隔离） |
| 适合场景 | 旧项目兼容、极轻量 UI | 现代项目、高清 UI、国际化、富文本 |

**核心结论**：TMP 的单次文本更新成本比传统 Text 高，但动态图集的全局稳定性好得多。大多数项目中，级联刷新带来的帧率抖动比单次成本差异更致命——所以 TMP 更受青睐。

## 16.6 文本性能优化实战

1. **字体预热**：启动时预先请求常用字符，避免运行时首次遇到触发动态生成
   ```csharp
   font.RequestCharactersInTexture("0123456789ABCDEFGHIJKLMNOPQRSTUVWXYZ你好世界开始退出设置");
   ```

2. **避免高频 text 赋值**：不要每帧改 text。需要实时刷新数值时，先判断内容是否真的变了再赋值

3. **禁用 Best Fit**

4. **减少 Rich Text 嵌套深度**

5. **动态文本区域单独 Canvas**：防止一次 text 更新触发整个界面 Canvas 重建

6. **TMP 的 Sprite/Emoji**：注意 SubMesh 带来的额外 DrawCall，大量使用需评估

7. **TMP 尽量单 Atlas 覆盖**：跨 Atlas 的字符（如 ASCII 与 Emoji 混排）无法合批，各产生一个 DrawCall
8. **TMP 材质层数**：Face/Outline/Underlay/Overlay/Glow 每多启用一层，每字符顶点数增加，不必要不启用
9. **TMP 高频刷新**：字符数不变时 `SetText` 复用缓存，不触发全量排版，比传统 Text 更适合高频数值刷新

## 本章总结

```
文本渲染的核心链路：

字符串
  → 逐字符解析 Unicode
    → 查字体文件获取 Glyph 索引
      → 查字形图集获取 UV（不在图集 → 动态栅格化 → 写入图集 → 可能触发 textureRebuilt 级联）
        → 排版计算（Advance 累加 + 换行 + 对齐）
          → 生成每字符 Quad（4 顶点 × N 字符）
            → VertexHelper → Mesh → CanvasRenderer.SetMesh()
              → Canvas.BuildBatch() → GPU
```

文本系统不是"另一种 Image"——它是 UGUI 中 CPU 开销最大的子系统。原因就是**顶点数**：Image 固定 4 个顶点，Text 的顶点数 = 字符数 × 4，还要加上字符解析和排版计算的 CPU 时间。

**传统 Text → TMP 的演进本质**：把"像素颜色"换成"距离场"，把"单张动态图集"换成"Multi Atlas"，把"位图拉伸模糊"换成"Shader 实时算边缘"。代价是单次更新更贵、Shader 更重，但换来了全局稳定性——不会因为一个新字符把整个界面拖垮。
