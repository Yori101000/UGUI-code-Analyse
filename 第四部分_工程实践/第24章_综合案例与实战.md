## 24.1 背包系统：数据驱动架构

### 24.1.1 架构分层

```
┌──────────────┐
│   InventoryPanel   │  ← UI 层：只负责显示
├────────────────┤
│  InventorySystem  │  ← 逻辑层：增删改查、发通知
├────────────────┤
│  InventoryData    │  ← 数据层：纯数据容器
└──────────────────┘
```

核心原则：**数据是唯一可信来源**。获得物品 → 改数据 → 发事件 → UI 刷新。UI 不直接操作数据。

### 24.1.2 数据定义

```csharp
// 物品配置（来自 Excel/配表）
[System.Serializable]
public class ItemConfig
{
    public int Id;
    public string Name;
    public string Icon;
    public int MaxStack;
}

// 玩家实际持有的物品
[System.Serializable]
public class ItemData
{
    public int ItemId;
    public int Count;
}

// 背包数据容器
public class InventoryData
{
    public List<ItemData> Items = new();
}
```

### 24.1.3 背包逻辑层

```csharp
public class InventorySystem
{
    public static InventorySystem Instance { get; } = new();
    public InventoryData Data = new();
    public Action OnInventoryChanged;

    public void AddItem(int itemId, int count)
    {
        var item = Data.Items.Find(x => x.ItemId == itemId);
        if (item != null) item.Count += count;
        else Data.Items.Add(new ItemData { ItemId = itemId, Count = count });
        OnInventoryChanged?.Invoke();
    }

    public void RemoveItem(int itemId, int count)
    {
        var item = Data.Items.Find(x => x.ItemId == itemId);
        if (item == null) return;
        item.Count -= count;
        if (item.Count <= 0) Data.Items.Remove(item);
        OnInventoryChanged?.Invoke();
    }
}
```

### 24.1.4 UI 层

```csharp
public class InventoryItemView : MonoBehaviour
{
    public Image icon;
    public TMP_Text countText;

    public void Refresh(ItemData data)
    {
        countText.text = data.Count.ToString();
        // icon.sprite = LoadIcon(data.ItemId);
    }
}

public class InventoryPanel : MonoBehaviour
{
    public Transform content;
    public InventoryItemView itemPrefab;
    private readonly List<InventoryItemView> itemViews = new();

    void OnEnable()
    {
        InventorySystem.Instance.OnInventoryChanged += Refresh;
        Refresh();
    }

    void OnDisable()
    {
        InventorySystem.Instance.OnInventoryChanged -= Refresh;
    }

    // ⚠ 初版：全量重建（数据少时可行，几百条时就卡了）
    void Refresh()
    {
        foreach (var v in itemViews) Destroy(v.gameObject);
        itemViews.Clear();
        foreach (var data in InventorySystem.Instance.Data.Items)
        {
            var v = Instantiate(itemPrefab, content);
            v.Refresh(data);
            itemViews.Add(v);
        }
    }
}
```

### 24.1.5 对象池优化

上述 `Refresh()` 每次全量 Destroy + Instantiate，300 个格子就卡。改为对象池：

```csharp
public class UIObjectPool<T> where T : Component
{
    private readonly Stack<T> pool = new();
    private readonly T prefab;
    private readonly Transform root;

    public UIObjectPool(T prefab, Transform root)
    {
        this.prefab = prefab;
        this.root = root;
        // 可以预创建 N 个
    }

    public T Get()
    {
        if (pool.Count > 0)
        {
            var obj = pool.Pop();
            obj.gameObject.SetActive(true);
            return obj;
        }
        return Object.Instantiate(prefab, root);
    }

    public void Release(T obj)
    {
        obj.gameObject.SetActive(false);
        pool.Push(obj);
    }
}
```

然后 `Refresh()` 改为：回收旧格子 → 从池取 → 刷新内容。不再 Instantiate/Destroy。

### 24.1.6 拖拽交换

使用 EventSystem 的 `IBeginDragHandler`/`IDropHandler` 实现格子交换：

```csharp
public class InventorySlotView : MonoBehaviour, IBeginDragHandler, IDragHandler, IEndDragHandler, IDropHandler
{
    public int Index;

    public void OnDrop(PointerEventData eventData)
    {
        var source = eventData.pointerDrag.GetComponent<InventorySlotView>();
        InventorySystem.Instance.Swap(source.Index, Index);
    }
}
```

`InventorySystem.Swap(indexA, indexB)` 交换两个格子数据后触发 `OnInventoryChanged`，UI 自动刷新。

## 24.2 虚拟列表：排行榜 10000 条数据

> 这部分和第 20 章 20.6.4 的虚拟列表原理相同。这里给完整可运行代码。

### 24.2.1 问题

```
for (int i = 0; i < 10000; i++)
    Instantiate(itemPrefab, content);
```

10000 个 Item = 10000 个节点 = Canvas 重建爆炸。屏幕只能看到十几个。

### 24.2.2 虚拟列表实现

```csharp
public class VirtualRankList : MonoBehaviour
{
    public ScrollRect scrollRect;
    public RectTransform content;
    public RankItemView itemPrefab;
    public float itemHeight = 100f;

    private List<RankData> dataList;
    private readonly List<RankItemView> items = new();
    private int visibleCount, poolCount;
    private int currentStartIndex = -1;

    void Start()
    {
        dataList = GenerateData(10000);
        Init();
    }

    void Init()
    {
        float viewportHeight = scrollRect.viewport.rect.height;
        visibleCount = Mathf.CeilToInt(viewportHeight / itemHeight);
        poolCount = visibleCount + 4;  // 缓冲区

        // 只创建 visibleCount + 4 个节点
        for (int i = 0; i < poolCount; i++)
            items.Add(Instantiate(itemPrefab, content));

        content.sizeDelta = new Vector2(content.sizeDelta.x, dataList.Count * itemHeight);
        scrollRect.onValueChanged.AddListener(_ => Refresh());
        Refresh();
    }

    void Refresh()
    {
        // Elastic 回弹时 anchoredPosition.y 会为负，必须钳到 0，
        // 否则 startIndex 变负 → dataIndex 越界
        float scrollY = Mathf.Max(0f, content.anchoredPosition.y);
        int startIndex = Mathf.FloorToInt(scrollY / itemHeight);
        if (startIndex == currentStartIndex) return;  // 没跨过行就不刷新
        currentStartIndex = startIndex;

        for (int i = 0; i < poolCount; i++)
        {
            int dataIndex = startIndex + i;
            if (dataIndex < 0 || dataIndex >= dataList.Count)   // 上下两端都要挡
            {
                items[i].gameObject.SetActive(false);
                continue;
            }
            items[i].gameObject.SetActive(true);
            items[i].GetComponent<RectTransform>().anchoredPosition =
                new Vector2(0, -dataIndex * itemHeight);
            items[i].Refresh(dataList[dataIndex]);
        }
    }
}
```

### 24.2.3 关键优化点

| 优化 | 效果 |
|------|------|
| 固定 poolCount（visibleCount+4） | 节点数不随数据量增长 |
| `startIndex` 无变化时不刷新 | 避免滚动时每帧刷新 |
| 不 Instantiate/Destroy | 零 GC |
| 手动设置 position | 不用 LayoutGroup，避免 Layout Rebuild |

### 24.3.2 UIBase 基类

public abstract class UIPanel : MonoBehaviour
{
    public virtual void OnCreate() { }  // 仅一次
    public virtual void OnOpen() { }    // 每次打开
    public virtual void OnClose() { }   // 关闭时
    public virtual void OnDestroyPanel() { }

### 24.3.3 UIManager

```csharp
public class UIManager : MonoBehaviour
{
    public static UIManager Instance;
    public Transform popupLayer;
    private readonly Stack<UIPanel> popupStack = new();

    void Awake() => Instance = this;

    public T Open<T>(T prefab) where T : UIPanel
    {
        T instance = Instantiate(prefab, popupLayer);
        instance.OnCreate();
        instance.OnOpen();
        popupStack.Push(instance);
        return instance;
    }

    // 关闭栈顶弹窗。注意这里刻意不带泛型参数——
    // 弹窗栈的语义就是"关最上面那个"，加个 T 只会让调用方误以为能指定关谁
    public void CloseTop()
    {
        if (popupStack.Count == 0) return;
        var panel = popupStack.Pop();
        panel.OnClose();
        Destroy(panel.gameObject);
    }

    // Android 返回键（旧输入系统写法；启用 Input System 包时改用
    // Keyboard.current.escapeKey.wasPressedThisFrame，见第 12 章 12.6）
    void Update()
    {
        if (Input.GetKeyDown(KeyCode.Escape))
            CloseTop();
    }
}
```

## 24.4 Profiler 性能诊断流程

### 24.4.1 定位

遇到卡顿，先不要改代码。打开 Profiler，看是 CPU 还是 GPU。

**CPU 热点**（Canvas.BuildBatch、LayoutRebuilder、GraphicRaycaster）：

```
PlayerLoop → UI → Canvas.BuildBatch  12ms  → Canvas 在频繁重建
PlayerLoop → UI → LayoutRebuilder     6ms  → Layout 在反复计算
PlayerLoop → UI → GraphicRaycaster    4ms  → 大量 Graphic 参与射线检测
```

**GPU 问题**（DrawCall 高）：

用 Frame Debugger 看 Batch 断裂原因：Material 不同？Texture 不同？Stencil 不同？

### 24.4.2 常见问题速查

| 问题 | Profiler 特征 | 原因 | 解决 |
|------|-------------|------|------|
| 每帧大量 Canvas.BuildBatch | CPU 持续高 | 有 UI 每帧 SetVerticesDirty | 加脏值判断，没变化不赋值 |
| LayoutRebuilder 持续高 | 滚动列表时 CPU 飙升 | 列表用了 LayoutGroup | 虚拟列表 + 手动 position |
| GraphicRaycaster 高 | 不操作时 CPU 也占用 | Graphic 未关 RaycastTarget | 关掉装饰性 Graphic 的 raycastTarget |
| GC Alloc 持续增长 | 内存曲线不断上升 | 每帧 new 字符串/List | 缓存复用、string.Format 改成条件判断 |
| Overdraw 高 | GPU 帧率高但卡 | 大量半透明 UI 叠加 | 减少全屏遮罩，控制重叠区域 |

### 24.4.3 优化检查清单

```
Canvas
□ 有没有超大 Canvas 导致局部变化触发全量重建？
□ 高频更新区域是否已拆分到独立子 Canvas？

Layout
□ ScrollView 是否用了 LayoutGroup？（建议手动设 position）
□ ContentSizeFitter 是否在频繁触发递归计算？

Graphic
□ 不必要的 Graphic 是否关了 RaycastTarget？
□ 装饰性元素（背景、边框、纯文字）的 raycastTarget = false？

渲染
□ 图集是否统一？（Frame Debugger 看 Batch 断裂原因）
□ 是否有不必要的 Mask？

GC
□ Update 里有没有每帧 new string/List？
□ 频繁打开关闭的 UI 是否用了对象池？
```

## 24.5 Profiler 实战：从抓到修

24.4 给出了诊断流程，这一节用三个案例演示完整走通"发现问题 → 定位根因 → 修复实现"。

> ⚠️ 下面出现的耗时与 DrawCall 数字都是**示意值**，用来说明 Profiler 读数长什么样、量级关系如何，**不是可复现的基准**——它们取决于 Unity 版本、目标设备、Editor 还是 Build、UI 复杂度。你自己项目的数字一定不一样，请以目标设备上的实测为准。这一节真正要传达的是**排查路径**，不是具体数值。

### 24.5.1 案例一：背包列表滚动卡顿

#### 现象

背包打开时第一次滚动不卡，滚动到中间区域后出现明显的帧率下降。

#### 抓取

1. 打开 Profiler（Window → Analysis → Profiler）
2. 切换到 Timeline 模式
3. 录制背包操作
4. 找到卡顿帧

#### 分析

在卡顿帧中，`LayoutRebuilder.Rebuild` 占用 **8.2ms**：

```
Profiler Timeline 卡顿帧：
  ├── Canvas.SendWillRenderCanvases: 9.1ms
  │   ├── LayoutRebuilder.Rebuild: 8.2ms  ← 瓶颈
  │   │   └── VerticalLayoutGroup.SetLayoutVertical
  │   │       └── 遍历 80 个子节点
  │   ├── Graphic.Rebuild: 0.7ms
  │   └── Canvas.BuildBatch: 0.2ms
```

#### 定位

代码发现 Content 使用 `VerticalLayoutGroup` + `ContentSizeFitter`：

```csharp
// 问题代码：每次添加物品触发全量 Layout Rebuild
void AddItem(ItemData data)
{
    var item = Instantiate(itemPrefab, contentTransform);
    // item 加入 → VerticalLayoutGroup 重新排布所有 80 个已有 item
}
```

ContentSizeFitter + VerticalLayoutGroup 的组合意味着每次新增 Item 时：LayoutGroup 重新遍历所有子节点计算尺寸，ContentSizeFitter 调整 Content 高度，ScrollRect 重新计算滚动范围。当 item 数量达到 80 时，一次完整的 Layout Rebuild 耗时 8ms。

#### 修复

**方案：对象池 + 固定高度 + 移除 ContentSizeFitter**

```csharp
public class OptimizedBagList : MonoBehaviour
{
    [SerializeField] private float itemHeight = 120f;
    private Queue<ItemSlot> pool = new Queue<ItemSlot>();

    public void AddItem(ItemData data)
    {
        var slot = GetFromPool();
        slot.Bind(data);
        // 手动设置位置，不触发 Layout Rebuild
        slot.rectTransform.anchoredPosition = new Vector2(0, -currentIndex * itemHeight);
        currentIndex++;
    }
}
```

#### 结果

| 指标 | 优化前 | 优化后 |
|------|--------|--------|
| LayoutRebuilder.Rebuild | 8.2ms | 0ms |
| Graphic.Rebuild | 0.7ms | 0.3ms |
| 总帧耗时 | 12ms | 3ms |

### 24.5.2 案例二：HUD 每帧重建

#### 现象

游戏运行时 Profiler 中每帧都出现 `Graphic.Rebuild`，即使 HUD 数据没有变化。

#### 抓取

1. Profiler 切换到 Hierarchy 模式
2. 按 `Graphic.Rebuild` 排序
3. 观察调用栈

```
Profiler Hierarchy:
  Graphic.Rebuild (每帧 15 次)  ← 异常
  ├── Text.SetVerticesDirty
  │   └── (调用栈中有 Animator.Evaluate)
  ├── Image.SetVerticesDirty
      └── (调用栈中有 Animator.Evaluate)
```

#### 定位

发现 HUD 根对象上挂了一个 Animator，有一个空动画（无关键帧）在持续播放：

```csharp
// 问题：空动画持续播放，导致每帧调用 OnDidApplyAnimationProperties
// → SetAllDirty() → 所有 Graphic 每帧重建
```

从源码可以确认：

```csharp
// Graphic.cs
protected override void OnDidApplyAnimationProperties()
{
    SetAllDirty();  // 动画属性应用后全标记
}
```

#### 修复

```csharp
// 方案 A：停止不需要的动画
void Start()
{
    animator.enabled = false;  // 关闭无用的 Animator
}

// 方案 B：将动画中的 UI 分离到独立 Canvas
// HUD Canvas（静态） + AnimCanvas（动画）
```

#### 结果

`Graphic.Rebuild` 从每帧 15 次降为 0，帧耗时降低 4ms。

### 24.5.3 案例三：Mask 导致 DrawCall 暴增

#### 现象

Frame Debugger 中 DrawCall 数量远超预期。场景中只使用了 10 个 UI 元素，DrawCall 却有 15。

#### 抓取

1. Window → Analysis → Frame Debugger → Enable
2. 逐条检查 DrawCall

```
Frame Debugger:
  DrawCall #0: UI/Default, TextureA, Stencil Ref=0  ← Mask 外的 Image
  DrawCall #1: UI/Default, TextureA, Stencil Ref=2  ← Mask 内的 Image
  DrawCall #2: UI/Default, TextureA, Stencil Ref=0  ← Mask 外的 Image
  DrawCall #3: UI/Default, TextureA, Stencil Ref=2  ← Mask 内的 Image
  ...
```

材质和纹理完全一样，Stencil Ref 却在 0 和 2 之间来回跳。

#### 定位

**先排除一个常见误判**：这不是"每个 Mask 内元素都有自己的 Stencil Ref"。`StencilMaterial.Add()` 是**带缓存**的——相同的 `(baseMaterial, stencilID, op, comp, ...)` 参数组合返回同一个 Material 实例，所以**同一层 Mask 下的所有子元素共享同一份材质，它们彼此完全可以合批**（详见第 15 章 15.1.7）。

真正的原因是**渲染顺序穿插**。UGUI 严格按 Hierarchy 顺序渲染，不会为了合批调整次序：

```
Hierarchy 实际顺序：
  Image_A     (Mask 外, Ref=0)  ┐
  MaskPanel                      │  Ref 在 0/2 之间反复横跳
    └ Image_B (Mask 内, Ref=2)  │  → 每跳一次断一次批
  Image_C     (Mask 外, Ref=0)  │
  MaskPanel2                     │
    └ Image_D (Mask 内, Ref=2)  ┘
```

Ref=0 的元素本可以合成一批、Ref=2 的也可以，但它们在 Hierarchy 里交替排列，中间被对方隔断，只能各自成批。**这和第 20 章 20.1「渲染顺序的影响」讲的是同一件事**，只是这里的状态差异来自 Stencil 而不是材质。

#### 修复

```csharp
// 方案 A：调整 Hierarchy 顺序，把同 Stencil 状态的元素排在一起
//   Image_A, Image_C  （Ref=0，连续）
//   MaskPanel + MaskPanel2 下的内容（Ref=2，连续）
// → 状态不再交替 → 批次数降到"状态种类数"

// 方案 B：矩形裁剪场景改用 RectMask2D
// 不创建材质实例，同一裁剪矩形下的元素可以合批；
// 注意跨不同 RectMask2D 之间仍会断批（见第 15 章），
// 但断批粒度是"每个裁剪区一次"，远好于 Mask 的"每个 Stencil 深度一次 + 材质实例"
```

#### 结果

| 方案 | 相对批次数 | 说明 |
|------|---------|------|
| 原始（Mask 内外在 Hierarchy 中交替） | 最多 | 每次 Stencil 状态切换断一次批 |
| 按 Stencil 状态重排 Hierarchy | 明显下降 | 降到接近"状态种类数" |
| 矩形场景换 RectMask2D | 最少 | 无材质实例，同一裁剪区内合批 |

> 具体降到几个批次取决于 UI 结构，请以自己项目的 Frame Debugger 为准。

## 本章总结

三个案例 + 一个诊断流程，覆盖了 UGUI 项目落地的核心问题：

```
背包系统 → 数据驱动架构（数据和 UI 分离）
虚拟列表 → 节点复用（只创建可见节点，滚动了不创建新节点）
弹窗系统 → 分层 + 生命周期管理（统一调度，避免散落）
Profiler 诊断 → 先定位再优化（不要凭感觉改代码）
```

24.5 的三个实战案例把诊断流程落到具体问题：背包卡顿是 Layout 全量重建，HUD 每帧重建是空动画触发 `SetAllDirty`，Mask 断批是 Stencil 状态在 Hierarchy 中反复切换。三者分别对应布局、重建、合批三个层面的典型性能陷阱。
