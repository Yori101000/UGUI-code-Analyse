# 第4章 UI 更新与重建系统

> 本章对应原书结构第4章内容。UI 更新与重建系统是 UGUI 的**调度中枢**，控制着所有 UI 元素何时、以何种顺序触发重建。理解这套机制，是排查 UI 性能问题和掌握 UGUI 生命周期的基础。

---

## 概述

UGUI 采用**保留模式（Retained Mode）**，核心思想是：UI 属性变化时**不会立即重建**，而是通过 **Dirty Flag（脏标记）** 记录变化，延迟到统一的时间点集中处理。这套机制的核心组件有三个：

| 组件 | 职责 |
|------|------|
| **CanvasUpdateRegistry** | 调度中心，持有重建队列，监听渲染事件 |
| **ICanvasElement** | 可重建元素的接口规范 |
| **Dirty Flag** | 标记位，记录哪些数据需要更新 |

整个重建链路的宏观时序：

```
UI 属性变化
  → 设置 Dirty Flag（仅标记，不执行）
  → Canvas 触发 willRenderCanvases 事件
  → CanvasUpdateRegistry.PerformUpdate()
    → Layout Rebuild（阶段 0-2）
    → ClipperRegistry.Cull（裁剪更新）
    → Graphic Rebuild（阶段 3-4）
    → Canvas.BuildBatch()（合批提交，native 方法）
```

## 4.1 延迟重建机制（Deferred Rebuild）

### 4.1.1 为什么需要延迟重建

假设一个 Button 在 OnClick 中同时修改了 Text 的文字、Image 的颜色和整个容器的位置。如果每次属性变化都立即触发重建：

```
修改 Text.text → 立即重建 Text（OnPopulateMesh + SetMesh）
修改 Image.color → 立即重建 Image（OnPopulateMesh + SetMesh）
修改 RectTransform → 立即计算布局
```

一帧内**三次重建**，其中两次是浪费的——因为 GPU 只关心最终状态，不关心中间过程。

延迟重建的优化思路：

```
修改 Text.text → 标记 m_VertsDirty = true（O(1)，几乎零开销）
修改 Image.color → 标记 m_VertsDirty = true
修改 RectTransform → 标记 Layout Dirty

下帧统一时机 → PerformUpdate()
  → 一次 Layout Rebuild
  → 两次 Graphic Rebuild（Text 和 Image 各一次）
  → 一次 Canvas.BuildBatch()
```

### 4.1.2 Dirty Flag 的设计

在 `Graphic.cs` 中，Dirty Flag 是三个布尔字段：

```csharp
// Graphic.cs
public class Graphic : UIBehaviour, ICanvasElement {
    private bool m_VertsDirty;     // 顶点需要重建
    private bool m_MaterialDirty;  // 材质需要更新
    // LayoutDirty 由 LayoutRebuilder 管理
}
```

这三个标记分别对应三个设置方法：

```csharp
public virtual void SetVerticesDirty() {
    if (!IsActive()) return;
    m_VertsDirty = true;
    CanvasUpdateRegistry.RegisterCanvasElementForGraphicRebuild(this);
    m_OnDirtyVertsCallback?.Invoke();
}

public virtual void SetMaterialDirty() {
    if (!IsActive()) return;
    m_MaterialDirty = true;
    CanvasUpdateRegistry.RegisterCanvasElementForGraphicRebuild(this);
    m_OnDirtyMaterialCallback?.Invoke();
}

public virtual void SetLayoutDirty() {
    if (!IsActive()) return;
    LayoutRebuilder.MarkLayoutForRebuild(rectTransform);
    m_OnDirtyLayoutCallback?.Invoke();
}
```

**关键观察**：这三个方法的共同点都是**只打标记 + 注册到队列**，不执行实际重建。

## 4.2 CanvasUpdateRegistry：调度中心

`CanvasUpdateRegistry` 是整个 UGUI 更新系统的**发动机**。它不是 MonoBehaviour，不通过 Unity 生命周期自动执行，而是通过事件驱动。

### 4.2.1 事件注册

```csharp
// CanvasUpdateRegistry.cs（简化）
public class CanvasUpdateRegistry {
    private static CanvasUpdateRegistry s_Instance;

    protected CanvasUpdateRegistry() {
        // 关键：监听 Canvas 的 willRenderCanvases 事件
        Canvas.willRenderCanvases += PerformUpdate;
    }

    private static CanvasUpdateRegistry instance {
        get {
            if (s_Instance == null)
                s_Instance = new CanvasUpdateRegistry();
            return s_Instance;
        }
    }
}
```

`Canvas.willRenderCanvases` 是 Unity 引擎在**每帧渲染之前**触发的 C# 事件。这意味着：

- UI 重建发生在**所有 MonoBehaviour.Update() 执行完毕之后**
- 发生在 **GPU 开始渲染之前**
- 一帧内只执行一次

### 4.2.2 两个重建队列

CanvasUpdateRegistry 维护两个独立的队列，分别对应布局重建和图形重建。注意实际源码中队列类型是 `IndexedSet`（兼具 O(1) 查重和有序遍历），而非 `List`：

```csharp
// 源码路径：Runtime/UGUI/UI/Core/CanvasUpdateRegistry.cs
public class CanvasUpdateRegistry {
    private readonly IndexedSet<ICanvasElement> m_LayoutRebuildQueue = new IndexedSet<ICanvasElement>();
    private readonly IndexedSet<ICanvasElement> m_GraphicRebuildQueue = new IndexedSet<ICanvasElement>();

    public static void RegisterCanvasElementForLayoutRebuild(ICanvasElement element) {
        instance.InternalRegisterCanvasElementForLayoutRebuild(element);
    }

    private bool InternalRegisterCanvasElementForLayoutRebuild(ICanvasElement element) {
        if (m_LayoutRebuildQueue.Contains(element))
            return false;
        return m_LayoutRebuildQueue.AddUnique(element);
    }

    public static void RegisterCanvasElementForGraphicRebuild(ICanvasElement element) {
        instance.InternalRegisterCanvasElementForGraphicRebuild(element);
    }

    private bool InternalRegisterCanvasElementForGraphicRebuild(ICanvasElement element) {
        if (m_PerformingGraphicUpdate) {
            Debug.LogError("Trying to add for graphic rebuild while already inside a rebuild loop.");
            return false;
        }
        return m_GraphicRebuildQueue.AddUnique(element);
    }
}
```

**两个队列的区分**：
- `m_LayoutRebuildQueue` —— 存放 `LayoutRebuilder` 实例（布局重建）
- `m_GraphicRebuildQueue` —— 存放 `Graphic` 实例（顶点/材质重建）

### 4.2.3 ICanvasElement 接口

所有能进入重建队列的元素都必须实现 `ICanvasElement` 接口：

```csharp
public interface ICanvasElement {
    void Rebuild(CanvasUpdate executing);  // 重建逻辑
    Transform transform { get; }           // 关联的 Transform（用于排序）
    void LayoutComplete();                 // 布局阶段完成后回调
    void GraphicUpdateComplete();          // 图形重建完成后回调
    bool IsDestroyed();                    // 是否已销毁
}
```

`Graphic` 和 `LayoutRebuilder` 都实现了这个接口，因此可以统一由 `CanvasUpdateRegistry` 调度。

## 4.3 PerformUpdate：完整的重建执行

这是整个 UI 更新系统的**核心方法**。它的执行顺序决定了 Layout 和 Graphic 的先后关系。

### 4.3.1 源码逐段分析

```csharp
// 源码路径：Runtime/UGUI/UI/Core/CanvasUpdateRegistry.cs
private void PerformUpdate() {
    // ── 准备阶段：清理无效元素 ──────────────────────────
    // 过滤已销毁的 ICanvasElement（通过 IsDestroyed 判断）
    CleanInvalidItems();

    // ── 排序阶段：按层级深度排序 ────────────────────────
    // 布局队列按 ParentCount（从根到叶子的深度）升序排列
    // 保证父级先布局，子级后布局——子级的布局依赖父级的尺寸结果
    m_LayoutRebuildQueue.Sort(s_SortLayoutFunction);

    // ── 第一阶段：Layout Rebuild ────────────────────────
    // 0=Prelayout, 1=Layout, 2=PostLayout
    m_PerformingLayoutUpdate = true;
    for (int i = 0; i <= (int)CanvasUpdate.PostLayout; i++) {
        for (int j = 0; j < m_LayoutRebuildQueue.Count; j++) {
            var rebuild = m_LayoutRebuildQueue[j];
            try {
                if (ObjectValidForUpdate(rebuild))
                    rebuild.Rebuild((CanvasUpdate)i);
            } catch (Exception e) {
                Debug.LogException(e, rebuild.transform);
            }
        }
    }
    // 布局完成后通知所有元素，然后清空队列
    for (int i = 0; i < m_LayoutRebuildQueue.Count; ++i)
        m_LayoutRebuildQueue[i].LayoutComplete();
    m_LayoutRebuildQueue.Clear();
    m_PerformingLayoutUpdate = false;

    // ── 中间阶段：裁剪更新 ──────────────────────────────
    ClipperRegistry.instance.Cull();

    // ── 第二阶段：Graphic Rebuild ───────────────────────
    // 3=PreRender, 4=LatePreRender
    m_PerformingGraphicUpdate = true;
    for (int i = (int)CanvasUpdate.PreRender; i < (int)CanvasUpdate.MaxUpdateValue; i++) {
        for (int k = 0; k < m_GraphicRebuildQueue.Count; k++) {
            try {
                var element = m_GraphicRebuildQueue[k];
                if (ObjectValidForUpdate(element))
                    element.Rebuild((CanvasUpdate)i);
            } catch (Exception e) {
                Debug.LogException(e, m_GraphicRebuildQueue[k].transform);
            }
        }
    }
    // 图形重建完成后通知所有元素，然后清空队列
    for (int i = 0; i < m_GraphicRebuildQueue.Count; ++i)
        m_GraphicRebuildQueue[i].GraphicUpdateComplete();
    m_GraphicRebuildQueue.Clear();
    m_PerformingGraphicUpdate = false;
}
```

### 4.3.2 阶段顺序的可视化

```
PerformUpdate()
│
├── 1. CleanInvalidItems()          ← 移除已销毁元素
│
├── 2. 排序 Layout 队列             ← 按 ParentCount 升序（父→子）
│
├── 3. Layout Rebuild（阶段 0-2）
│   ├── Prelayout    (0)
│   ├── Layout       (1)
│   └── PostLayout   (2)
│
├── 4. LayoutComplete() + 清空队列
│
├── 5. ClipperRegistry.Cull()       ← RectMask2D 裁剪
│
├── 6. Graphic Rebuild（阶段 3-4）
│   ├── PreRender     (3)
│   └── LatePreRender (4)
│
├── 7. GraphicUpdateComplete() + 清空队列
│
└── 结束
```

**为什么 Layout 必须在 Graphic 之前？**

布局计算会改变 UI 元素的位置和尺寸（RectTransform）。如果先重建顶点再计算布局，顶点数据就是基于旧位置的，布局变化后会错位。因此必须先布局、后生成顶点。

**为什么 ClipperRegistry.Cull 在中间？**

RectMask2D 的裁剪依赖于布局计算后的最终位置。布局完成后计算哪些元素被裁剪、哪些需要剔除，然后 Graphic Rebuild 阶段根据裁剪结果决定是否生成顶点。

## 4.4 CanvasUpdate 枚举

```csharp
public enum CanvasUpdate {
    Prelayout     = 0,  // 布局前：UI 元素在此阶段执行布局前的准备工作
    Layout        = 1,  // 布局：核心布局计算（LayoutGroup.SetLayoutHorizontal/Vertical）
    PostLayout    = 2,  // 布局后：布局完成后的清理或调整
    PreRender     = 3,  // 渲染前：Graphic 在此阶段重建顶点和材质
    LatePreRender = 4,  // 渲染后前：Graphic 的后处理（如 TMP 的额外操作）
}
```

在实际源码中，Layout Rebuild 遍历 `Prelayout → Layout → PostLayout`，Graphic Rebuild 遍历 `PreRender → LatePreRender`。

### 各阶段的用途

| 枚举值 | 阶段 | 典型用途 |
|--------|------|---------|
| `Prelayout` (0) | 布局前 | 重置布局缓存、计算子元素的最小/首选尺寸 |
| `Layout` (1) | 布局 | 执行 `ILayoutController.SetLayoutHorizontal()` 和 `SetLayoutVertical()` |
| `PostLayout` (2) | 布局后 | 清理布局状态、处理布局完成后的回调 |
| `PreRender` (3) | 渲染前 | Graphic 的 `UpdateGeometry()` 和 `UpdateMaterial()` |
| `LatePreRender` (4) | 渲染后前 | 某些组件需要在顶点生成后额外处理的逻辑 |

### LayoutRebuilder 对各阶段的响应

```csharp
// LayoutRebuilder.cs（简化）
public void Rebuild(CanvasUpdate executing) {
    switch (executing) {
        case CanvasUpdate.Layout:
            // 执行布局计算
            PerformLayoutCalculation();  // 自下而上：子 → 父
            PerformLayoutControl();      // 自上而下：父 → 子
            break;
        case CanvasUpdate.PostLayout:
            // 清理布局标志
            break;
    }
}
```

## 4.5 Graphic Rebuild 的完整链路

Graphic 的 `Rebuild()` 在 `PreRender` 阶段执行。它根据 Dirty Flag 分别处理顶点和材质：

### 4.5.1 Graphic.Rebuild()

```csharp
// Graphic.cs（简化）
public virtual void Rebuild(CanvasUpdate update) {
    if (update == CanvasUpdate.PreRender) {
        // 顶点脏了 → 重建网格
        if (m_VertsDirty) {
            UpdateGeometry();
            m_VertsDirty = false;
        }
        // 材质脏了 → 更新材质
        if (m_MaterialDirty) {
            UpdateMaterial();
            m_MaterialDirty = false;
        }
    }
}
```

### 4.5.2 UpdateGeometry → OnPopulateMesh → SetMesh

这是 UGUI 中"UI 生成网格"的核心路径：

```csharp
// Graphic.cs（main，简化）
// 注意：s_VertexHelper 和 workerMesh 都是静态共享实例，不是每次 new
private static readonly VertexHelper s_VertexHelper = new VertexHelper(Allocator.Domain);

protected virtual void UpdateGeometry() {
    DoMeshGeneration();
}

private void DoMeshGeneration() {
    if (rectTransform != null && rectTransform.rect.width >= 0 && rectTransform.rect.height >= 0)
        OnPopulateMesh(s_VertexHelper);   // 子类填充顶点（自己负责先 Clear）
    else
        s_VertexHelper.Clear();

    // 链式调用 IMeshModifier（Shadow / Outline 等）
    var components = ListPool<Component>.Get();
    GetComponents(typeof(IMeshModifier), components);
    for (var i = 0; i < components.Count; i++)
        ((IMeshModifier)components[i]).ModifyMesh(s_VertexHelper);
    ListPool<Component>.Release(components);

    s_VertexHelper.FillMesh(workerMesh);        // 写入静态共享 Mesh
    canvasRenderer.SetMesh(workerMesh);         // 提交到 CanvasRenderer
}

// 虚方法：子类重写以生成不同的网格
protected virtual void OnPopulateMesh(VertexHelper vh) {
    // 默认行为：生成一个覆盖整个矩形区域的 Quad
    // Image/Text 重写此方法
}
```

> `s_VertexHelper` 用 `Allocator.Domain` 分配原生内存，不进 C# GC 堆；`Clear()` 只重置计数、不释放容量。详见第 2 章 2.4 / 2.7 与第 5 章 5.5.3。

### 4.5.3 UpdateMaterial

```csharp
// Graphic.cs（main，简化）
protected virtual void UpdateMaterial() {
    if (!IsActive()) return;

    canvasRenderer.materialCount = 1;
    // materialForRendering 内部依次调用所有 IMaterialModifier.GetModifiedMaterial()
    // Mask 的 Stencil 材质就是在这条链上注入的
    canvasRenderer.SetMaterial(materialForRendering, 0);
    canvasRenderer.SetTexture(mainTexture);
}
```

### 4.5.4 完整调用链整理

```
Graphic.Rebuild(CanvasUpdate.PreRender)
│
├── UpdateGeometry()
│   └── DoMeshGeneration()
│       ├── OnPopulateMesh(s_VertexHelper)   ← 虚方法，子类实现（静态共享实例）
│       │   ├── Image: 根据 ImageType 生成顶点
│       │   ├── Text:  根据 TextGenerator 生成顶点
│       │   └── RawImage: 生成覆盖区域 Quad
│       ├── IMeshModifier 链 ModifyMesh(s_VertexHelper) ← Shadow / Outline
│       ├── s_VertexHelper.FillMesh(workerMesh)  ← 写入静态共享 Mesh
│       └── canvasRenderer.SetMesh(workerMesh)   ← 提交到 CanvasRenderer
│
└── UpdateMaterial()
    ├── canvasRenderer.materialCount = 1
    ├── canvasRenderer.SetMaterial(materialForRendering, 0) ← IMaterialModifier 链
    └── canvasRenderer.SetTexture(mainTexture)
```

## 4.6 Dirty 标记的触发链

### 4.6.1 哪些操作会触发 SetVerticesDirty

> ⚠️ 注意：UGUI 中**没有** `SetColor()` / `SetSprite()` / `SetType()` / `SetText()` / `SetFontSize()` 这类方法。这些都是**属性 setter**，内部先用 `SetPropertyUtility.SetStruct/SetClass/SetColor` 判断值是否真的变了，变了才调 Dirty 方法。

| 操作 | 源码路径 |
|------|---------|
| 修改 `Graphic.color` | `Graphic.color` setter → `SetVerticesDirty()` |
| 修改 `Image.sprite` | `Image.sprite` setter → `SetAllDirty()`（顶点 + 材质 + 布局都可能受影响） |
| 修改 `Image.type` | `Image.type` setter → `SetVerticesDirty()` |
| 修改 `Text.text` | `Text.text` setter → `SetVerticesDirty()` + `SetLayoutDirty()` |
| 修改 `Text.fontSize` | `Text.fontSize` setter → `SetVerticesDirty()` + `SetLayoutDirty()` |
| 尺寸变化 | `Graphic.OnRectTransformDimensionsChange()` → `SetVerticesDirty()`（+ 布局） |
| 子类主动调用 | 任何需要重建网格的场景，直接调 `SetVerticesDirty()` |

### 4.6.2 哪些操作会触发 SetMaterialDirty

| 操作 | 源码路径 |
|------|---------|
| 给 `Graphic.material` **赋值** | `Graphic.material` setter → `SetMaterialDirty()`（**读取 getter 不触发**，见第 20 章 20.2） |
| Mask 启/停 | `MaskUtilities.NotifyStencilStateChanged` → `IMaskable.RecalculateMasking()` → `SetMaterialDirty()` |

### 4.6.3 哪些操作会触发 SetLayoutDirty

| 操作 | 源码位置 |
|------|---------|
| 修改 `RectTransform` 尺寸 | 内部自动触发 |
| `LayoutGroup` 的属性变化 | `LayoutGroup.OnDidApplyAnimationProperties()` 等 |
| 子对象加入/移出 | `LayoutGroup.OnTransformChildrenChanged()` |
| `ContentSizeFitter` 启用 | `ContentSizeFitter.OnEnable()` |

### 4.6.4 传播方向

Layout Dirty 是**向上传播**的：

```
子节点 RectTransform 变化
  → 子节点调用 SetLayoutDirty()
    → LayoutRebuilder.MarkLayoutForRebuild(子节点的 rectTransform)
      → 向上查找最近的 LayoutGroup 父节点
        → 将找到的 LayoutGroup 注册到 m_LayoutRebuildQueue
```

Graphic Dirty 是**自身注册**的：

```
Image.color 变化
  → SetVerticesDirty()
    → CanvasUpdateRegistry.RegisterCanvasElementForGraphicRebuild(this)
      → 把自己加入 m_GraphicRebuildQueue
```

## 4.7 性能陷阱：每帧 Dirty

**典型反例——每秒刷新 60 次的 HP 文本：**

```csharp
void Update() {
    hpText.text = player.currentHP.ToString();
}
```

这段代码每帧做了以下事情：
1. `Text.text` 的 setter 调用 `SetVerticesDirty()`
2. 注册到 `m_GraphicRebuildQueue`
3. 下一帧 `PerformUpdate()` 遍历队列
4. `Graphic.Rebuild()` → `UpdateGeometry()` → `OnPopulateMesh()` → 生成全部文本顶点 → `SetMesh()`

对于 Text 组件，`OnPopulateMesh()` 涉及 **`cachedTextGenerator.PopulateWithErrors()`** ——这是引擎内部的排版引擎，会遍历每一个字符执行排版计算。频繁调用会导致明显的 CPU 开销。

**排查方法**：在 Profiler 的 Timeline 中观察 `Graphic.Rebuild`、`Canvas.SendWillRenderCanvases` 的调用频率。如果每帧出现，说明有 UI 元素每帧被标记为 Dirty。

```csharp
// 临时调试：在 SetVerticesDirty 中打印调用栈（需修改源码或使用 Harmony 注入）
public virtual void SetVerticesDirty() {
    Debug.Log($"[{name}] SetVerticesDirty\n{StackTraceUtility.ExtractStackTrace()}");
    // ... 原有逻辑
}
```

## 4.8 Animation 系统与重建的交互

### 4.8.1 动画修改 UI 的路径

当 Animation/Animator 驱动 UI 属性时，Unity 在动画采样完成后触发重建：

```
MonoBehaviour.Update() 完成
  → Animator.Evaluate()（采样动画曲线）
    → 通过 C# 属性 Setter 赋值
    → Setter 内部调用 SetVerticesDirty() / SetMaterialDirty()
  → 引擎检测到"有 UI 属性被动画修改"
  → Canvas.willRenderCanvases 触发
  → CanvasUpdateRegistry.PerformUpdate()
```

从 `Graphic.cs` 源码可以确认：`color` setter 调用 `SetVerticesDirty()`，`material` setter 调用 `SetMaterialDirty()`。另外 Unity 在动画属性应用后调用 `OnDidApplyAnimationProperties()`，其实现为 `SetAllDirty()`——即动画驱动会标记所有脏类型。

### 4.8.2 不同属性的重建成本

| 属性 | 触发 | 重建范围 | 适合 |
|------|------|---------|------|
| `CanvasGroup.alpha` | 无 | 仅修改 alpha，无 Rebuild | 高频动画：淡入淡出 |
| `Graphic.color` | `SetVerticesDirty` | 仅该 Graphic 的 Mesh | 中等频率：颜色渐变 |
| `RectTransform` 尺寸 | `SetLayoutDirty` | 向上传播至 LayoutGroup，全子树递归 | 低频或独立 Canvas |
| `Text.text` | `SetVerticesDirty` | `PopulateWithErrors()` 遍历所有字符 | 字符数少或独立 Canvas |

### 4.8.3 陷阱：全 Canvas 扩散

Animator 驱动一个 Button 的 color → `OnDidApplyAnimationProperties()` → `SetAllDirty()` → 下一帧全 Canvas 的 BuildBatch 重跑。解法：动画中的 UI 移到独立小 Canvas。

### 4.8.4 Animator vs DoTween

| 维度 | Animator | DoTween |
|------|---------|---------|
| 触发 | `SetAllDirty()`（全标记） | 仅对应 Setter 触发 |
| 额外开销 | 引擎做全 Canvas 动画检测 | 无额外检测 |
| 适用 | 复杂多属性动画序列 | 简单单属性过渡 |

## 4.9 关键源码位置速查

## 总结

UI 更新与重建系统是 UGUI 的"调度心脏"。理解它需要抓住三个核心认知：

1. **延迟重建**：属性变化时不立即执行，只打 Dirty Flag，保证了"一帧内多次修改只触发一次重建"
2. **两阶段分离**：Layout Rebuild 在前（解决"在哪"），Graphic Rebuild 在后（解决"长什么样"），中间插入 ClipperRegistry.Cull
3. **调度中心**：`CanvasUpdateRegistry.PerformUpdate()` 通过监听 `Canvas.willRenderCanvases` 事件，在每帧渲染前统一执行所有待处理的重建

这套设计使得 UGUI 在复杂的 UI 场景下仍能保持高效的更新——将"零散的即时重建"转变为"统一的批处理重建"。
