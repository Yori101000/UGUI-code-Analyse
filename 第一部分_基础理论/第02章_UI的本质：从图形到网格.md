# 第2章 UI的本质：从图形到网格

> 本章先从 RectTransform（UI 元素的坐标系）入手，再揭示 UGUI 最核心的底层逻辑：**所有 UI 元素最终都是 Mesh（网格）**。理解这一点，才能真正理解 UGUI 的运作方式。

---

## 2.1 从 RectTransform 入手：UI 元素的"空间"

在谈"UI 是 Mesh"之前，先回答一个更基础的问题：**UI 元素放在哪里？**

一个 UI 元素在场景中是一个带 `RectTransform` 的 GameObject。`RectTransform` 定义了它的**矩形区域**：位置（锚点 + 轴心）、尺寸、旋转与缩放。渲染时，这个矩形区域就是网格生成的"画布"——`Graphic` 子类（Image/Text）读取 `rectTransform.rect`，把矩形区域转成顶点：

```
RectTransform（矩形：位置 + 尺寸）
    ↓ 读取 rectTransform.rect
Graphic.OnPopulateMesh()（第 5 章）
    ↓
Mesh（顶点 + 三角形）
```

所以理解 UGUI 渲染的坐标系起点是 RectTransform：**UI 的位置和尺寸由 RectTransform 决定，渲染内容由 Graphic 生成，二者通过 `rectTransform.rect` 连接**。锚点/轴心/offsetMin/offsetMax 等完整机制在第 3 章专门展开，这里只需要记住这一条链路。

### 核心论点：UI在GPU眼中是Mesh

开发者眼中看到的是"按钮"、"图片"、"文本"，但这些概念在GPU层面**根本不存在**。

GPU只知道三件事：

- **顶点（Vertex）**：空间中的点，含位置、颜色、纹理坐标等信息
- **三角形（Triangle）**：三个顶点构成一个三角形面
- **渲染状态（Render State）**：纹理、材质、混合模式

所谓"渲染一个Image"，其实就是构造两个三角形拼成一个矩形，贴上纹理。所谓"渲染一段Text"，就是把每个字符的轮廓（glyph）拆解成顶点和三角形，贴上字体纹理。

**UI的本质，是将高层的视觉描述（"这里有一张图"）转换为底层的几何描述（"这里是6个顶点、4个三角形"）。**

## 2.2 从UI到Mesh的转换链

UGUI的整个渲染流程可以抽象为一条数据转换链：

```
UI描述（Image/Text等组件）
    ↓  OnPopulateMesh()
顶点数据（UIVertex 顶点流 NativeArray + ushort 三角形索引）
    ↓  SetMesh()
CanvasRenderer（数据容器）
    ↓  Canvas.BuildBatch() （Native层）
合并Mesh + DrawCall → GPU Command Buffer
    ↓  RenderPipeline 调度
GPU：Vertex Shader → 光栅化 → Fragment Shader → 像素输出
```

这条链路的起点，是每个`Graphic`子类重写的`OnPopulateMesh`方法。

## 2.3 UIVertex —— 顶点的数据结构

UGUI用`UIVertex`结构体表示一个顶点。它位于`UnityEngine.UI`命名空间，但**不属于 uGUI 仓库**——它是引擎侧 `UnityEngine.UIModule` 内置类型，uGUI 的 `VertexHelper.cs` 只是引用它：

```csharp
// UnityEngine.UIModule（引擎侧，不在 uGUI 仓库内；下为 Unity 6 / main 对应字段）
public struct UIVertex
{
    public Vector3 position;          // 顶点位置（UI 为局部坐标，Z 通常为 0）
    public Vector3 normal;            // 法线（UI默认是 (0, 0, -1) ）
    public Vector4 tangent;           // 切线（用于法线贴图等，默认 (1,0,0,-1)）
    public Color32 color;             // 顶点颜色（支持渐变）
    public Vector4 uv0;               // 主纹理坐标（Vector4，前两位是 UV）
    public Vector4 uv1;               // 第二套纹理坐标
    public Vector4 uv2;               // 第三套纹理坐标（TMP 的 SDF 参数用）
    public Vector4 uv3;               // 第四套纹理坐标
    public Vector4 prevPosition;      // 上一帧顶点位置（存于 TEXCOORD4 / UV4 通道，main 新增）
}
```

注意：**uv0~uv3 的类型是 `Vector4` 而非 `Vector2`**——多余的两位用于向 Shader 传递额外参数（如 TMP 在 uv2.z/uv2.w 中传递 SDF 阈值）。`prevPosition` 记录上一帧顶点位置，uGUI 仓库中通过 `TEXCOORD4` 通道读写（见下节 `FillMesh` 的 9 通道布局）。

关键理解：

- **`position`**：顶点的三维坐标。UI虽然显示在2D屏幕上，但Unity使用3D坐标系，Z轴用于控制渲染层级（类似PS的图层顺序）。
- **`color`**：每个顶点独立的颜色，这是实现UI渐变的底层基础。Image组件的"Image Type = Filled"就是通过修改部分顶点的颜色/位置来实现的。
- **`uv0`**：纹理采样坐标，范围[0,1]。Image的Sprite纹理映射、Text的字体图集映射都依赖此字段。
- **`normal`和`tangent`**：在标准UI渲染中不常用，但在自定义Shader实现光照效果时是必需的。

## 2.4 VertexHelper —— 网格构建工具

`VertexHelper`是UGUI提供的一个辅助类，用于简化Mesh的构建过程。它是`OnPopulateMesh`方法的**唯一参数**。

```csharp
// VertexHelper.cs (UGUI main，路径：Runtime/UGUI/UI/Core/Utility/VertexHelper.cs)
public class VertexHelper : IDisposable
{
    private NativeArray<UIVertex> m_Verts;    // 顶点流（AoS 交错存储）
    private NativeArray<ushort>   m_Indices;  // 三角形索引（ushort）

    private int m_VertCount;    // 当前顶点数（逻辑长度）
    private int m_VertCapacity; // 已分配顶点容量
    private int m_IndexCount;   // 当前索引数
    private int m_IndexCapacity;// 已分配索引容量

    const int k_InitialVertCapacity  = 64;    // 初始顶点容量
    const int k_InitialIndexCapacity = 96;    // 初始索引容量
    const int k_MaxVertCount = 65000;         // 顶点数上限

    public VertexHelper() : this(Allocator.Persistent) { }
    internal VertexHelper(Allocator allocator);   // Graphic 内部使用 Allocator.Domain

    // 清空数据：只重置计数，不释放 NativeArray
    public void Clear() { m_VertCount = 0; m_IndexCount = 0; }

    // 添加一个顶点
    public void AddVert(UIVertex v);
    public void AddVert(Vector3 position, Color32 color, Vector4 uv0);
    public void AddVert(Vector3 position, Color32 color, Vector4 uv0, Vector4 uv1,
                        Vector4 uv2, Vector4 uv3, Vector3 normal, Vector4 tangent, Vector4 prevPosition);

    // 添加三角形（三个索引构成一个三角形面）
    public void AddTriangle(int idx0, int idx1, int idx2);

    // 添加一个四边形（两个三角形，4个顶点）
    public void AddUIVertexQuad(UIVertex[] verts);

    // 将数据填充到Mesh对象
    public void FillMesh(Mesh mesh);

    // 获取当前顶点/索引数量
    public int currentVertCount { get; }
    public int currentIndexCount { get; }
}
```

与旧实现（并行 `List` 逐通道存储）不同，当前 main 把顶点打包成**单流（AoS）NativeArray**，字段顺序与 GPU 顶点布局一一对应。要点：

- **容量只增不减**：首次使用按 64（顶点）/ 96（索引）分配，扩容时取 `NextPowerOfTwo`；`Clear()` 不释放容量，只有 `Dispose()` 才释放原生内存。
- **`Clear()` 是"逻辑清空"**：只把 `m_VertCount` / `m_IndexCount` 置零，数组里的旧数据等待被后续填充覆盖。
- **顶点上限 65000**：`FillMesh` 在 `m_VertCount >= 65000` 时抛异常；索引使用 `ushort`（16 位无符号上限 65535），与该上限匹配。
- **`FillMesh` 单流上传**：`SetVertexBufferParams` 声明 9 通道布局（Position / Normal / Tangent / Color / TexCoord0~3 / TexCoord4=prevPosition），一次 `SetVertexBufferData` 把整个 `m_Verts` 上传，索引走 `SetIndexBufferData`（`UInt16`）。

典型的调用模式：

```csharp
protected override void OnPopulateMesh(VertexHelper vh)
{
    vh.Clear();                          // 1. 清空旧数据（重置计数）
    vh.AddVert(pos1, color1, uv1);       // 2. 添加顶点
    vh.AddVert(pos2, color2, uv2);
    vh.AddVert(pos3, color3, uv3);
    vh.AddVert(pos4, color4, uv4);
    vh.AddTriangle(0, 1, 2);             // 3. 添加三角形
    vh.AddTriangle(2, 3, 0);
}
```

`VertexHelper`屏蔽了直接操作`Mesh`对象的复杂性，开发者只需要关注"顶点在哪里、什么颜色、对应纹理的哪个位置"。

## 2.5 Image组件的网格生成

`Image`组件是UGUI中使用最频繁的组件。其网格生成逻辑在`Image.OnPopulateMesh`中实现。

### 2.5.1 简单模式：一个矩形

当Image没有任何特殊设置（Simple类型，无边框）时，它生成一个矩形Mesh——4个顶点、2个三角形（共6个索引）：

```csharp
// Image.cs (简化示意)
protected override void OnPopulateMesh(VertexHelper vh)
{
    vh.Clear();
    Rect r = GetPixelAdjustedRect();

    // 四个顶点：矩形四个角
    vh.AddVert(new Vector3(r.xMin, r.yMin), color, new Vector2(0, 0));
    vh.AddVert(new Vector3(r.xMin, r.yMax), color, new Vector2(0, 1));
    vh.AddVert(new Vector3(r.xMax, r.yMax), color, new Vector2(1, 1));
    vh.AddVert(new Vector3(r.xMax, r.yMin), color, new Vector2(1, 0));

    // 两个三角形构成矩形
    vh.AddTriangle(0, 1, 2);
    vh.AddTriangle(2, 3, 0);
}
```

对应关系：

UV 原点在**左下角**（与上面代码里 `(0,0)` 对应 `r.yMin` 一致）：

```
(0,1)───────(1,1)   ← 上边 (yMax)
  │ tri0   /  │
  │     /     │
  │  /   tri1 │
(0,0)───────(1,0)   ← 下边 (yMin)
```

### 2.5.2 九宫格（Sliced）模式

当Sprite有边框（border）时，Image启用了Sliced模式。此时网格不再是4个顶点，而是一个**3x3的网格**——最多16个顶点、18个三角形，将图片分为9个区域，四个角保持原始大小，四个边拉伸，中间平铺或拉伸。

这是UI适配不同尺寸背景框的核心机制。

### 2.5.3 Filled模式

Filled模式通过动态修改顶点位置和三角形索引来实现"径向填充"或"左右/上下填充"效果（常用于技能冷却、血条等）。其本质是**根据填充比例重新计算每个顶点的坐标和三角形分布**。

## 2.6 Text组件的网格生成

Text的网格生成远比Image复杂。每个字符（glyph）都需要被转换为一个四边形（4个顶点、2个三角形），然后拼接到同一个Mesh中：

```csharp
// Text.cs (简化示意)
protected override void OnPopulateMesh(VertexHelper vh)
{
    vh.Clear();
    // 遍历每个字符，从Font中获取glyph信息
    foreach (char c in text)
    {
        CharacterInfo info;
        font.GetCharacterInfo(c, out info, fontSize);

        // 每个字符生成一个四边形
        // 顶点位置由字符的advance、bearing等排版数据决定
        // UV坐标对应字体图集中该字符的位置
        vh.AddVert(topLeft,     color, info.uvTopLeft);
        vh.AddVert(bottomLeft,  color, info.uvBottomLeft);
        vh.AddVert(bottomRight, color, info.uvBottomRight);
        vh.AddVert(topRight,    color, info.uvTopRight);

        vh.AddTriangle(vertIndex + 0, vertIndex + 1, vertIndex + 2);
        vh.AddTriangle(vertIndex + 2, vertIndex + 3, vertIndex + 0);
    }
}
```

每个字符的详细参数（`CharacterInfo`）：

| 字段 | 含义 |
|------|------|
| `index` | 字符在字体图集中的索引 |
| `advance` | 字符前进宽度（字符间距基准） |
| `bearing` | 字符偏移量（水平/垂直） |
| `glyphWidth / glyphHeight` | 字形尺寸 |
| `uvBottomLeft / uvTopRight` | 在字体图集中的纹理坐标范围 |

一段文本最终生成的顶点数 = **字符数 × 4**，三角形数 = **字符数 × 2**。一个"Hello World"就有44个顶点、22个三角形。

## 2.7 UIVertex 内存布局与 GC 代价

### 2.7.1 UIVertex 内存大小

```csharp
public struct UIVertex
{
    public Vector3 position;    // 12 bytes (3×f32)
    public Vector3 normal;      // 12 bytes (3×f32)
    public Vector4 tangent;     // 16 bytes (4×f32)
    public Color32 color;       //  4 bytes (4×u8)
    public Vector4 uv0;         // 16 bytes (4×f32)
    public Vector4 uv1;         // 16 bytes (4×f32)
    public Vector4 uv2;         // 16 bytes (4×f32)
    public Vector4 uv3;         // 16 bytes (4×f32)
    public Vector4 prevPosition;// 16 bytes (4×f32，main 新增，存于 TEXCOORD4)
}
```

字段合计 124 字节；在 IL2CPP 下考虑对齐，一个 UIVertex 占用 **约 128 字节**。

### 2.7.2 VertexHelper 的内存管理

从源码看，`Graphic.cs` 使用**静态共享**的 `s_VertexHelper`：

```csharp
private static readonly VertexHelper s_VertexHelper = new VertexHelper(Allocator.Domain);
```

这意味着：
- 所有 Graphic 组件**共用同一个 VertexHelper 实例**
- 填充前先 `Clear()`（各 Graphic 子类通常在自身 `OnPopulateMesh` 开头调用），**不释放已分配的 NativeArray 容量**
- `Clear()` 只将计数置零，底层原生数组保留，继续复用

```csharp
// VertexHelper.cs (main，简化)
public void Clear()
{
    m_VertCount = 0;   // 只重置计数，不缩容、不释放
    m_IndexCount = 0;
}
```

与旧版本最大的区别：存储从托管 `List` 换成了 `Allocator` 管理的 **NativeArray**。`Graphic` 传入 `Allocator.Domain`，表示内存随 Domain 卸载自动回收、不进入 C# GC 堆；只有 `Dispose()` 会显式释放。

### 2.7.3 内存占用放大

VertexHelper 内部的 `NativeArray<UIVertex>` 会随着**历史最大值**增长，且**永远不会缩容**：

```
首次重建 Text，100字符：
  400 顶点 → NativeArray 按 2 的幂扩到 512 容量 → 512 × 128B ≈ 64KB（Native 内存，不触发 C# GC）

后续 Text 更新为 50 字符：
  仍使用已有 512 容量的数组，零分配

后续 Text 更新为 200 字符：
  800 顶点 → 扩容到 1024 → 128KB（触发一次 Native 重分配 + 拷贝）

Text 再变回 50 字符：
  1024 容量保留，不缩容
```

**结论：VertexHelper 的 NativeArray 容量 = 当前帧所有 Graphic 中顶点数的历史峰值（向上取 2 的幂）。**

### 2.7.4 IMeshModifier 的分配

`DoMeshGeneration()` 中通过 `GetComponents<IMeshModifier>` 获取修改器列表：

```csharp
var components = ListPool<Component>.Get();
GetComponents(typeof(IMeshModifier), components);
```

`ListPool<Component>` 从对象池获取临时 List，用完归还。此处无额外 GC 分配。

### 2.7.5 FillMesh 的代价

`s_VertexHelper.FillMesh(workerMesh)` 将顶点数据写入共享 Mesh：

```
FillMesh 内部（main，单流上传）：
  mesh.SetVertexBufferParams(m_VertCount, s_VertexLayout);  // 声明 9 通道布局
  mesh.SetIndexBufferParams(m_IndexCount, IndexFormat.UInt16);
  mesh.SetVertexBufferData(m_Verts, ...);                   // 一次 memcpy 上传全部顶点
  mesh.SetIndexBufferData(m_Indices, ...);                  // 索引上传
  mesh.SetSubMesh(0, ...);
  mesh.RecalculateBounds();

每帧覆盖：
  → 顶点/索引缓冲区按新大小重新设置（Native 内存操作）
  → 无托管数组中转，省去旧实现逐通道 List→数组的搬运
```

共享 Mesh 避免了每帧 `new Mesh()` 的 GC 分配；`FillMesh` 本身仍有 Native 内存操作，但比旧实现（逐通道 `SetVertices/SetUVs/...`）更紧凑。

### 2.7.6 性能影响量化

| 场景 | 每帧分配 | 说明 |
|------|---------|------|
| 一个 Image（4 顶点） | 极少 | 数据量小，可忽略 |
| 100 字符 Text | ~64KB VertexHelper 上限（512 顶点 × 128B） | NativeArray 不缩容，一次性膨胀 |
| ScrollView 中 10 个 Text 同时更新 | ~430KB 顶点数据入 Mesh | 集中在 Graphic Rebuild 阶段 |
| Shadow（顶点×2） | 上浮 2 倍 | 顶点复制，非新分配 |
| Outline（顶点×5） | 上浮 5 倍 | 最坏情况 |

### 2.7.7 优化方向

- 高频更新的 Text 限制字符数，避免 VertexHelper 容量膨胀
- 滚动列表中优先复用已有 UI 节点，而非每帧重建
- 使用 TextMeshPro（其内部有独立的字符缓存管理，见第 16 章）
- 场景卸载后触发 `Resources.UnloadUnusedAssets()` 回收 Native Mesh 内存

## 2.8 CanvasRenderer 的数据提交（链路收尾）

`FillMesh` 把顶点写入 Mesh 之后，`Graphic` 调用 `canvasRenderer.SetMesh(workerMesh)` 把 Mesh 交给 CanvasRenderer。这条"生成 → 提交"链路的完整代码（`DoMeshGeneration()`，含 IMeshModifier 链）在第 5 章 5.5.3 展开，这里只记三个结论：

- **`SetMesh` 只是暂存**：CanvasRenderer 保存数据，不立即触发渲染。
- **真正的提交在 `Canvas.BuildBatch()`**：引擎 Native 层读取所有 CanvasRenderer 的数据，合并同材质同纹理的 Mesh 后提交 DrawCall（第 6 章）。
- **CanvasRenderer 是"数据容器"**：它只存不处理，机制详见第 8 章。

SetMesh 暂存的数据：

```
CanvasRenderer
├── Mesh（顶点 + 三角形索引）
├── Material（Shader + 渲染状态）
├── Texture（主纹理）
├── cull（是否裁剪）
└── sortingOrder（排序顺序）
```

`Canvas.BuildBatch()`在C#侧没有源码，其逻辑可以理解为：

```
Canvas.BuildBatch(): 收集所有 CanvasRenderer → 按材质/纹理/层级排序分组
  → 同组内 Mesh 合并 → 提交 DrawCall 到 GPU（详见第 6 章）
```

## 本章总结

| 概念 | 实质 |
|------|------|
| Image | 一个矩形Mesh + Sprite纹理 |
| Text | N个矩形Mesh + 字体图集纹理 |
| 按钮交互 | 通过射线检测判断Mesh边界 |
| 透明度 | 顶点颜色的Alpha通道 |
| UI动画 | 逐帧修改顶点位置或颜色 |

UGUI本质上是一个 **"UI描述 → 几何网格"的数据构建系统**。它在每一帧做的工作，就是把高层UI描述转译为GPU可以理解的顶点和三角形。这个视角转换，是后续理解DrawCall合并、UI批处理、自定义Mesh特效、合批优化等一系列高级主题的**逻辑起点**。

> 接下来：第 3 章展开 RectTransform 的完整机制（2.1 只讲了它作为"顶点生成范围"的那一面），第 4、5 章讲这些顶点什么时候、由谁生成。至于生成好的 Mesh 如何被组织到一起、实现高效的 DrawCall 合并——那是**第 9 章 UI 批处理与 DrawCall** 的主题。
